# Runtime optimization (2026-07-25 → )

Goal: cut extraction wall time without regressing peptides. S30, `-threads 100`, 128-core
ibminode05. Baseline: **27:54 wall, 10,104–10,138 peptides**.

## Profiling (baseline, `time -v` + built-in stage timers)

| metric | value |
|---|---|
| wall | 27:54 |
| avg CPU | 5680% (57 of 100 cores) |
| **system time** | **34,858 s (37% of all CPU)** |
| **voluntary context switches** | **195,478,195** |
| peak RSS | 139 GB |
| stage split (window loop) | trace 60%, score 37%, materialize/emit ~2% |
| serial preamble | ~2.5 min (frame load + MS1 tracing) before the window loop |

## Adversarial review (codex + vibe; kimi silent)

Both named the same #1: the **nested-topology cap `n_conc = n_threads / n_bands = 100/12 = 8`** —
only 8 of 24 windows run concurrently, each reserving 12 threads even during single-threaded phases.
The 96-thread target is hit only while all 8 trace at once; phase-skew + the 3-wave tail (24/8)
collapse the average. codex also flagged the "trace 60%" timer is wall-summed-per-window, so
lock-waits are charged to "trace". Verified real bugs: (a) `perf:trace_bands=0` auto mode traced
serially (the call re-read the raw 0 → 1 band); (b) EPD program-global critical hit from inside the
parallel loop.

My CPU data settled which finding dominates the **37% system time / 195M context switches**: the
**ElutionPeakDetection global critical**, exercised because our config runs `ms1/ms2_split_valleys=7.0`
(vibe wrongly assumed valley-splitting off → "0%").

## Iteration 1 (commit 4cbe972): EPD fix + heavy-first scheduling + auto-band bug

Three peptide-preserving runtime changes.

| metric | baseline | iter 1 | delta |
|---|---|---|---|
| **system time** | 34,858 s | **664 s** | **−98% (52×)** |
| **voluntary ctxsw** | 195M | **177k** | **−99.9% (1100×)** |
| total CPU | 95,131 s | 68,564 s | **−28%** |
| **wall** | 27:54 | **29:09** | **+4.5% (flat/worse)** |
| peptides | ~10,120 | 10,033 | −0.7% |

**Key lesson — system time was a RED HERRING for wall.** The 195M context switches were threads
*blocking* on the EPD lock (not burning wall), so removing the contention freed 28% of CPU but did
not shorten wall — and serializing EPD's detection lost its parallelism, ~canceling out. This is a
**throughput/energy win** (28% less CPU per file matters for running many files on a shared node),
not a **latency win**. After the fix the tool uses ~39 of 100 cores honestly; the wall ceiling is
the `n_conc=8` topology. Peptides −0.7% (just outside the 0.34% replicate band): most likely EPD
push-back reordering exposing a downstream order-sensitivity; to attribute next.

EPD patch is `patches/openms-epd-no-nested-parallel.patch` (an OpenMS file, not in the speXtract
tree). Heavy-first + auto-band are in `src/DIAPseudoSpectra.cpp`.

## Iteration 2 (running): topology sweep

`n_conc = 100 / trace_bands`, so `trace_bands ∈ {12,8,6,4}` sweeps `n_conc ∈ {8,12,16,24}` with no
code change. Tests whether more concurrent windows (fewer bands, better phase-skew averaging +
shorter tail) beats fewer windows (more bands, less total trace CPU — banding cuts trace work
superlinearly). The old "12 beats 24 bands" was measured under the contention-ridden EPD; the
balance may have shifted. Metric: wall at no peptide regression.

**Result — the reviewers' #1 wall recommendation is FALSIFIED. More concurrent windows is
monotonically SLOWER:**

| bands | n_conc | wall | CPU% | peptides |
|---|---|---|---|---|
| **12** | **8** | **28:40** | **4008%** | 10,101 |
| 8 | 12 | 31:38 | 3432% | 10,127 |
| 6 | 16 | 35:04 | 2446% | 10,099 |
| 4 | 24 | 39:19 | 1898% | 10,108 |

vibe predicted n_conc=24 → 2.5–3× faster; it is 37% SLOWER (39:19 vs 28:40), and CPU utilisation
FALLS with more windows (40 → 19 cores). Banding (intra-window) is where the real parallel work
is — and fewer bands also means more total trace CPU (banding cuts trace work superlinearly). So
**b12/n_conc=8 is the wall-optimal topology; it is already tuned.** Peptides flat across all arms
(10,099–10,127), which also resolves iter-1's −0.7%: b12 here is 10,101, so rt1's 10,033 was
variance and the EPD change is peptide-neutral.

## Where the wall actually goes

At b12 the tool uses **40 of 100 cores** (4008%). The 60 idle cores are lost to *within-window
phase serialisation*: only the trace (12-band) and score (p_team) phases are ~12-way parallel;
materialize, grid, EPD valley-split, and emit run ~8-way (one thread per concurrent window). With
8 windows phase-skewed, the average lands at ~40. The prime suspect is EPD (iter-1 made it
serial-internal; it runs on both MS1 and MS2 at `split_valleys=7.0`). Ceiling if the serial phases
were fully parallel: ~68,000 CPU-s / 100 + preamble ≈ 12–14 min (~2×), NOT via topology (tuned)
but via parallelising the serial phases or a task-graph that overlaps them.

## The bottleneck, measured: EPD valley-splitting is ~54% of wall

`split_valleys=0` (EPD off), clean same-node on ibminode05: **13:18 wall** vs b12 EPD-on **28:40**.
So EPD adds ~15.4 min (~54% of wall) and ~36,600 CPU-s (b12 68,900 − EPD-off 32,311, ~53% of
compute). The built-in stage timers hid it inside "trace" because they are CPU-summed-per-window,
and a SERIAL phase dominates wall-clock even at modest CPU-share.

**But EPD-off still runs at only 41 cores** (same as EPD-on's 40). So the ~40-core ceiling is
STRUCTURAL phase-skew, not EPD-specific: every window runs its phases serially, only trace (12-band)
and score (p_team) are ~12-way, and materialize/grid/emit are ~8-way — with 8 phase-skewed windows
the average is ~40. Parallelising any one phase cannot lift the systemic ceiling.

## Iterations 3–5: EPD parallelisation + topology — all exhausted, REVERTED

Made OpenMS EPD lock-free (per-thread accumulation, no `OPENMS_ElutionPeakDetection_mtraces`
critical) and folded valley-splitting into the trace parallelism two ways, plus tested
oversubscription:

| variant | wall | cores | peptides |
|---|---|---|---|
| **b12 (iter-1, shipped)** | **28:40** | 40 | **10,101** |
| iter-3: EPD per-band | 27:27 | 44 | 10,016 |
| iter-4: EPD balanced parallel-for | 26:53 | 44 | 10,016 |
| iter-5: oversubscribe n_conc=16 (−threads 200) | 28:13 | 51 | ~10,101 |

EPD parallelisation caps at ~44 cores / −6% wall — the 8-window phase-skew limits per-window EPD
to ~12-way effective. And it costs **0.8% peptides DETERMINISTICALLY** (iter-3 = iter-4 = 10,016
exactly): chunking the traces before the split reorders them, and the pipeline's peptide output is
order-sensitive at ~0.8%. Oversubscription (iter-5) raised active cores to 51 but wall did NOT
improve — the extra cores went to context switches (1.9M+5M). **All of iters 3–5 reverted**; the
shipped state is iter-1 (clean, +28% CPU-efficiency, no peptide regression).

## Verdict and roadmap

Incremental and topology levers are exhausted; wall is ~27–28 min, ~40–44 core bound. Real gains
need the pipeline **flattened** so a single 100-thread pool works across all windows/phases instead
of 8 windows each running phases serially:
* **EPD-only flatten** (all windows MTD → one global 100-way EPD pass → per-window grid/score):
  EPD 15.4 min → ~6 min (36,600 CPU-s / 100), total ~19 min = **~1.5×**. Moderate rewrite:
  `detectTraces_` must return RAW MassTraces, the window loop splits into two passes, and all
  windows' raw traces are held between them (~EPD-off peak RSS, feasible on 1 TB).
* **Full task-graph** (materialize/MTD-band/EPD/grid/score as tasks with `depend` clauses on one
  persistent team): total compute 68,900 CPU-s / 100 + preamble ≈ **~14 min = ~2×**. Larger, the
  codex recommendation.

Both are correctness-GATED (emitted-spectrum count + peptides must match b12's 1,528,083 / 10,101),
which was NOT gambled overnight at 3am against the no-regression constraint. They are the clear next
step for careful daytime implementation. **Also flagged: the ~0.8% order-dependence of peptide
output is a reproducibility issue worth fixing independently of runtime.**
