# Window-loop stage breakdown, and a 1.79x speedup (S30)

## The measurement that should have come first

`phase_clock_` was never called between the start of the window loop and its end. Every claim
about where its ~86% of runtime goes was **inference**, and two performance fixes were attempted
and reverted against that unverified model. Five atomic accumulators now time each stage.

**CPU-seconds summed across threads** (a stage on 20 threads contributes 20x its wall):

| stage | CPU-s | share |
|---|---|---|
| materialize | 16.9 | 0.10% |
| **trace** (`MassTraceDetection`) | **11,578** | **69.34%** |
| fraggrid | 292 | 1.75% |
| **score** | **4,811** | **28.81%** |
| emit | 1.2 | 0.01% |

## This corrects a conflation

`/proc` sampling had shown the loop's *tail* running 1,993 s at 1.000 user cores with 21 of 22
threads in `futex_wait`, and I generalised that to "scoring is the bottleneck". Both statements
are true and they are **different claims**:

* **scoring is the serial TAIL** — the last window's precursors, one core, everyone else idle
* **tracing is the BULK** — 69% of all CPU work in the loop

Two fixes were aimed at the tail on the strength of that conflation. The larger target was never
addressed.

## Result

| | before | after |
|---|---|---|
| wall | 4,428 s | **2,471 s** |
| peptides | 10,072 | **10,060 (−0.12%)** |
| vs diaTracer (457 s) | 9.7x | **5.4x** |

−0.12% is inside the 0.2% noise band, so this is a speedup at unchanged quality. It comes from
two changes together — MS1 band-parallel tracing (the MS1 call omitted the band argument the MS2
call already passed, so it ran single-threaded) and the `perf-3` precursor-level parallelism now
**capped** at `omp_get_max_threads()/n_conc`.

Uncapped, `perf-3` requested a full team per window — the same nested-oversubscription defect
diagnosed in `ElutionPeakDetection.cpp:328` and reproduced by omission a day later.

## What the breakdown says to do next

**Tracing is the target, and it is the one stage with no OpenMP of its own.**
`MassTraceDetection` walks an intensity-sorted apex list against a shared `peak_visited` bitset —
greedy-sequential by construction. Banding sidesteps that (a trace cannot span more than
`mass_error_ppm`, so m/z-disjoint bands cannot interact) and measured **2.6x on the MS1 phase**.

MS2 tracing already bands, but at `ceil(threads/windows)` = 5 for a 100-thread run. With 69% of
loop CPU there, raising the band count is the obvious next test — and it is cheap, because
banding is already implemented and already validated on MS1.

**Not** more work on scoring: at 28.8% it caps out at 1.4x even if made free.

## Still open

System time remains **40.9%** of CPU (32,199 s of 78,766 s) even with the cap. The
oversubscription is reduced, not eliminated — `ElutionPeakDetection.cpp:328` is still a bare
`#pragma omp parallel for` with no `num_threads`, reached from inside the loop, and capping it
directly changed output (−7.2% peptides) because its program-global critical guards a shared
output vector whose append order depends on team size.
