  **1. Medium — the "driver never reaches a task scheduling point" claim is false in `[det]` + integer-detector mode** — `src/diaspextract.cpp:6432` (claim at 7044).
  `loadTile` runs `toTof(kv.second)` on the driver when `detOn_() && integer_detector`, and `toTof` (1397) calls `forTasks_`/`parTasks_`, which with >131072 peaks and nthreads>1 creates a real taskloop — its taskgroup end is a task scheduling point on the driver.   **2. Medium — finished-but-unwritten tiles are bounded by team size, not by `pipe_depth`** — `src/diaspextract.cpp:7061-7067`.
  Each writer task spin-sleeps on a worker thread in `while (written < f)` and that spin is not a scheduling point, so it hogs the thread. Interleaving: 64 threads, `DIASPEXTRACT_PIPE_TILES=16`, a run whose windows complete faster than the mzML write drains (many small windows / fast tiles): tiles 0..14 finish, writer 0 writes, writers 1..14 are dequeued (FIFO, they precede later-admitted windows) and spin-hold 14 workers; more tiles finish on the remaining workers and spawn more writers until up to 62 workers sit spinning and only one writes. During that episode, up to ~62 tiles' `win_out` spectra are resident alongside the ≤16 tiles' slabs — peak RSS is O(n_threads × tile output + pipe_depth × slabs), not the "bounded by pipe_depth" the design claims. It self-corrects (writers drain in order, threads free, driver stalls at `left != 0` meanwhile — no deadlock, by the same FIFO induction), so this is a residency-bound violation, not a hang. Breaks invariant 5 as stated. Theoretical-to-rare on real data (heavy windows usually outlast writes).
