  ## Numbered answers

  **1. `stdSortPar_` / `parallelSortTotal_` / `sortExact_` / `mzOrder_` — fine.** `parallelSortTotal_` (296) is used only where the comparator is total by construction (index last key at 987-990 and 3873-3877); the merge-path split reproduces `std::merge`'s sequence exactly, and for a total order the sorted sequence is unique, so the result *is* `std::sort`'s, at any thread count. `sortExact_` (338) sorts a permutation with the index as last key and falls back to `std::sort` on the untouched vector when any equal-key neighbour exists — sound, and the tie count is order-independent (n − #distinct keys). `stdSortPar_` (392) is a statement-faithful replay of libstdc++ 13's `__introsort_loop` + `__final_insertion_sort` over disjoint ranges with the same depth budget, so equal keys land exactly as `std::sort` leaves them; its tasks aren't try/catch-wrapped, but the body cannot throw (no allocation, a no-throw double comparator at the only call site). Non-libstdc++-13 platforms (libc++/macOS, MSVC, other GCCs) take plain `std::sort` — the pre-scaling behaviour on that platform; cross-stdlib `std::sort` differences predate this range. `mzOrder_` (3795-3811): the identity shortcut is valid (strictly increasing ⇒ identity is the unique sorted order), and both consumers call the same helper on the same container, so they provably share one order.

  **2. `parallelSort_` callers — fine.** Two call sites: the seed-order segments (comparator ends `a > b` on unique indices — total, 1594-1597) and the `frag_traces` content sort (7183-7197), whose comparator is *not* total (`return false`) but compares every consumer-visible field including the full profile at 7192; equivalent traces differ only in arena offset and are observationally identical downstream, so any permutation gives the same output. `nt` varies with `omp_get_num_threads()` and `onPipeDriver_()` (including a window running undeferred on the driver past the libgomp task cliff, acknowledged at 7436-7439), but the output does not.

  **3. minlen — fine.** The sample is index-addressed (`part[i]`, every spectrum kept in place), the slices are a pure function of m/z, and detection runs the same code path on the same post-dnoise, post-prune map with the same bands and splitter as the run — so it is independent of thread count, tiling, stream-load and dnoise in the same sense the run's own trace set is (the e2e 1-vs-4-thread byte-identity check runs with minlen auto on). The brightest-tenth ranking's ties carry equal FWHM, so the selected multiset is tie-invariant; `q()` is deterministic; it runs once before the tile loop. See finding 7 for the missing upper bound.

  **4. isotol — fine, two notes.** The stride sample over the content-sorted traces is computed once, before the loop — tiling- and thread-independent; a loud `Precondition` throw guards the sortedness assumption. Grid argmax ties go to the *wider* tolerance (`J >= bj` keeps the later x) as documented. N < 2 → 0.05 fallback with an honest stamp. All-zero controls maximise J at the grid top → clamp 0.05, sensible. Notes: there is no minimum probe count (a 2-trace run "measures" from 2 probes — deterministic and clamped, but noisy; docs promise nothing); the stamped 3-decimal value is exactly the grid value used.

  **5. twin_rt_frames auto — fine with finding 2.** `cycle` is `frameSpacing(ms1_rt)`: the run-wide *minimum* positive MS1 frame gap, computed once at 5990 before tiling — per-run, and a minimum, not a median or mean (docs say only "the cycle", which is accurate, and the minimum makes the minlen floor conservative). Empty precursors or all-<3-point seed traces → n = 1, harmless. `cycle ≤ 0` (one MS1 frame) skips the whole block → same-frame fold and the 1.5.0 stamp text, the correct degenerate behaviour. Median via `nth_element` at `size/2` is the deterministic upper median. No upper bound on n: self-correcting for any plausible input (`rt_tol ≈ med + cycle/2`); pathological overflow is finding 2.

  **6. Cross-frame fold — no failing input found; one semantics note.** The relation is deterministic and input-order-independent: the pair search is a serial double scan over the (z, mz, rt, i) sort, examined from both directions, so the 20 ppm probe and the 0.05 ppm bin test (each taken on the probe's own m/z) are direction-independent in effect; the union-find and the survivor rule ((isotopes, peaks) strictly greater, ties to the earliest canonical index) are serial. The cell test uses the same monotone `(T − rt) > tile_drt` form as the tile loop's ownership test (7164-7165) over the run-level 600-s cell edges; tile edges are a subset of cell edges and the test is monotone in T, so same cell ⇒ same tile under every `cells_per_tile` (verified against 6541-6542 and the window cut at 7004-7007) — the fold sees the same candidate sets at 0, 1 and 2. `-1` ⇒ `rt_tol = 0` ⇒ `|dRT| ≤ 0` on the same doubles = the old (rt, z) grouping exactly, stamp included. Transitivity: yes, a same-frame pair and a cross-frame pair chain into one cluster, and the `ext` gate is *per pair* — a cluster needs only one ext-marked one-bin cross-frame link to absorb further same-frame members (span chains past `rt_tol` are counted in `st[4]`, and the selftest pins the chaining). That is the pre-1.6.0 cluster semantics extended, not a new leak: every member still satisfies the twin relation to some neighbour. `[twins]` counts pair *links* (the increment precedes the root check), so an already-connected pair is counted too — log-only.

  **7. F3 fused cap key — fine, one theoretical caveat.** `kq` is exactly the unfused key minus its intensity term for each `cap_rank` (rank 1: `max(c,0)²`; rank 2: `max(c,0)×(1+ov)`; rank 0: `c`, linear), and `frag_ai` is the same IM-weighted apex the unfused key uses, attenuated by foreign-envelope removal with it (4588). The same-bin merge sums `ai` over the same overlap set whose scores it maximises, and `kb` is updated only inside the overlap branch — consistent. "Never below the best piece's key" holds whenever `kq ≥ 0` (always for ranks 1/2; for rank 0 it needs the gate score `c > 0`, which admission ensures in practice — a hypothetical negatively-scored admitted fragment would break the doc sentence; theoretical). Ties resolve by m/z order; keys stay double until the recap float-array store, on one code path for pipelined and unpipelined, so no cross-path rounding.

  **8. Pipelined tile loop — fine, with the finding-8 residency nuance and one portability assumption.** Writes are strictly in tile order (writers spawned in order, chained on the `written` counter, `finishTile` byte-identical to the barrier path, mzPeak `all_out` appended inside it). The carry has a single owner per window (`CarryGate`, 6613): `take()` precedes the content sort where carried records enter; `publish()` follows it; the destructor publishes on every exit including `pipe_abort` early-outs, so no waiter waits forever; acquire/release ordering is correct. `teamHelpersQueued_` cannot leak — the decrement is the first statement of the spawned task and the region barrier runs every spawned task, abort or not; late helpers touch only their `shared_ptr` cursor. `onPipeDriver_` is reset after the catch at 7507 on every exit. `malloc_trim` between tiles is documented to only return what the finished tile left. Assumption worth naming: `CarryGate::wait` has no `taskyield` and is deadlock-free because thieves steal oldest-first, so every tile-k window starts before any tile-(k+1) window; that holds for libgomp and libomp (MSVC has no tasking and can't run this code at all). A runtime with newest-first stealing could park all workers on tile-(k+1) carries while tile-k windows sit queued — theoretical, not reachable on the supported toolchain.

  **9. Exception paths — sound by construction; coverage gap is finding 4.** Reader (`loadTile`) → driver `try` → `drvFail` → `pipe_abort`; window bodies catch everything into `worker_err` and always decrement `left`, and the `CarryGate` destructor still publishes, so abort can produce neither a hang nor a lost wake-up; `writeTile` wraps `finishTile`, records via `drvFail` and *always* advances `written`, so successor writers never spin forever; `teamFor_` rethrows the first chunk exception after all claimed chunks finish, and `teamAssist_` pullers route failures into the job's `err`, never into the assisting window. Everything reaches the main thread as `drv_err`/`worker_err` after the region → message + non-zero exit. `std::terminate` is not reachable on these paths (all task bodies wrapped; the unwrapped `introsortLoopPar_` tasks are no-throw, see Q1). A writer failure can leave a partial file on disk, but the run reports the error — never success. The e2e falsifier covers none of the pipe-only paths (finding 4).

Docs/help/scrub — findings 1, 5, 6; everything else checks out.** Verified against the code: 29 default stamps (24 + monocheck, foreign, fragment_fuse, ms1_min_length, iso_im_tolerance — all five on at defaults ✓); "(n + 0.5) × the cycle" in README/help ✓ 6354; "at least 1" ✓ 6349; "0.001 grid" ✓ (t = 0.002 + 0.001x, x ≤ 48); "[0.01, 0.05]" ✓; "200,000 probes" ✓ (stride = ⌈N/200000⌉); "fewer than 100 measurable traces fall back to 3 s" ✓ (`w.size() >= 100`); "within 0.05 ppm" ✓ `BIN_PPM`; "0.4 × median FWHM, at least half an MS1 cycle" ✓; controls "±50 ppm, where no isotope of the probe can sit" ✓ (≪ ISO/z at any m/z); the six-option reset sentence matches the code for spectra (header caveat = finding 1); "up to two tiles have windows in flight" ✓ (finding 8 nuances slabs, not windows); `ext` "nothing folds across frames without v2" ✓ (mono_ext set only at 4398).

  **11. b592804 — yes to both.** The updated 12b tests what its message claims — "the header does not record the twin setting": it asserts the default stamp starts "MS1 frames up to " and contains "(auto: ", that `-1` restores "same frame", and digest equality.   ## Summary

  The three headline invariants survive scrutiny: the parallel sorts are provably `std::sort`'s sequence where it matters and duplicate-insensitive where it doesn't; the per-run estimators are deterministic single-pass measurements taken before the tile loop; and the cross-frame fold's cell condition is exactly the tile-ownership condition, so output is tiling-invariant by construction. The one genuine breach of a stated invariant is finding 1 — the reset recipe doesn't restore the 1.5.0 header stamp, and the project's own digest design cannot detect that class of drift. Everything else is defensive: an unclamped division (2), an opt-in log race (3), a test-coverage gap on the machinery this release adds (4), and text-level scrub/doc issues (5, 6).
