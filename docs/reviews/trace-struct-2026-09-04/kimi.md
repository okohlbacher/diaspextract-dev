  # Review: TRACE-STRUCT-REDESIGN.md — verdict up front

  The core observation is right: `xi` is arithmetic, `xv` is the payload, `tof`+`b` is the authoritative m/z, and the arena kills three mallocs per trace. But the claim "PURE REPRESENTATION — the integer path's spectrum digest must not change" is **false as written**, for a reason the doc never engages with: the four cached doubles are *not* all derivable. Two of them (`mz`, `im` on the integer path; `mz`, `rt`, `im` on the OpenMS path) are detector *state*, and the accessor table in §3 of the doc silently redefines them. The doc also misses three zero-padding semantics changes that alter gate decisions, and one grid-denominator change that alters every Pearson score. Details below, section by section.

  ## 1. Is "one degree of freedom" true?

  **Mostly yes, with one structural caveat and one outright contradiction.**

  **(a) OpenMS detector → dense span.** `toTrace()` (src:297-320) sorts `(rtIndex, intensity)` pairs and pushes one entry per MassTrace peak. MassTraceDetection accepts at most one peak per spectrum (its `findBestPeak` picks a single closest peak per scan), so one-point-per-frame holds and a dense span with zeros is expressible. Two caveats the doc should assert rather than assume:

  - The global RT axis is `unique()`-ed (src:2590). Two spectra *of the same map* with an identical RT collapse to one axis index, and `toTrace` would then push two points with the same `xi` — unrepresentable in a dense span (two intensities, one slot). Today this is silently representable; under the redesign it must be an assert, like the `len < 65536` assert in the risk table.
  - For the OpenMS path the doc says `frame0` comes from "the index of the first peak's RT in the map's spectrum sequence." Fine — but note this makes `toTrace` depend on a per-map frame table that doesn't exist yet for the OpenMS path (which never builds a `PeakSlab`). That's new plumbing the doc waves at.

  **(b) EPD children as sub-spans — verified true, with one deletion caveat.** I read `ElutionPeakDetection::detectElutionPeaks_` in the patched OpenMS: children are built by copying a *contiguous index run* of the parent's peaks (`while (last_idx <= mins[min_idx]) tmp_mt.push_back(*cp_it)`, EPD source ~line 480-490), the valley minimum goes to the left child only, `mins.push_back(mt.getSize() - 1)` makes the children tile the parent exactly. No merging across parents (per-`mt` loop), no reordering, no fabricated points, intensities copied verbatim. So "child = `(frame0 + a, b - a, ...)` aliasing the parent's arena range" is sound. One caveat: `else if (maxes.empty()) return;` — EPD can *delete* a trace outright even with both filters off. That's today's behavior too, but it means the arena must tolerate parent ranges no child references (it does — append-only).

  **(c) `xt` — the doc's claim is half right, and the half that's wrong is load-bearing.** EPD's *split decision* uses only RT and (smoothed) intensity: m/z appears exactly twice in EPD — a debug `cout` (EPD:396) and `new_mt.updateWeightedMeanMZ()` *after* the split (EPD:536). So "EPD ignores per-peak m/z" is true of the geometry. **But the per-peak m/z must still be present in the MassTrace for `toTrace()` to behave as today**: the default `apex` estimator reads `mt[mt.findMaxByIntPeak(false)].getMZ()` (src:304), and `splitIntegerTraces` then sets `t.tof = ax.tofOf(t.mz, t.b)` (src:1039). The exact current value is `tofOf(mzOf(xt[apex], b_apex_frame), b_apex_frame)` — a **double round-trip through the calibration with an `llround`**, which is *not* guaranteed to be a fixed point. What would have to be true for the digest to survive: the child must be assigned exactly `tofOf(mzOf(parent_xt[a + apex_child], b), b)`, not `parent_xt[a + apex_child]` and not a slab re-lookup by (frame, intensity, approximate bin) — the latter is not provably unique (two peaks in one frame can share a float intensity near the parent centroid) and even a perfect lookup skips the round-trip. The honest fix is a *transient* per-point bin arena that lives from detection until the split joins, then dies. That partially resurrects the third allocation during exactly the phase whose peak the doc is trying to cut — say so in the doc. Also: for `trace:mz_estimator=mean`, the child's reported m/z is an intensity-weighted mean of *per-point* m/z over the child — unrecoverable from one `tof`. Default is `apex`, but the option exists and the doc's own risk row concedes this ("reverts to a centroid").

  ## 2. Zero-padding semantics — read the arithmetic, and three consumers break

  Zeros contribute exactly `+0.0` to sums, so anything that is a pure sum over the points in the same order is bit-safe. The problems are the statistics whose *denominators, counts, or sequences* change:

  - **Scorer `dot` / `overlap` (src:2162-2164).** The loop tests only `pv != 0.0f` (precursor side). A zero-padded *fragment* entry `(slot, 0.0)` with a non-zero precursor value leaves `dot` unchanged but **increments `overlap`** — a gap the fragment never had a point at now counts as co-elution evidence, and the `overlap < min_corr_pts` guard (src:2164) passes fragments that today fail. Fix: `if (gv.second == 0.0f || pv == 0.0f) continue`. The doc says this in §4 ("skipping arena == 0") but its §2 evidence sentence only mentions the precursor side — the fragment side is the one that breaks.
  - **`fsum`/`fsumsq` under `var_support_` (src:2181-2188).** The sums are zero-safe. **`n` is not**: `n = touched.size() + (supEnd-supBegin) - overlap`. With dense spans, `supEnd-supBegin` becomes `len` (span) instead of `np` (real points), and `touched` is inflated because the pdense fill (src:2116-2121) pushes a slot to `touched` even when `pval == 0` (`if (pdense[gi]==0) touched.push_back(gi); pdense[gi] += 0`). Both inflate `n`, both change `c`. Fixes: skip `pval == 0` before the `nearest_slot` lookup (also correct for default mode — `touched` then contains exactly today's slots), and carry a real-point count per trace (or count non-zeros in the `fsum` pass, which already iterates). The `supEnd-supBegin < min_corr_pts` early skip (src:2161) stays output-equivalent with `len` (it just skips less; the `overlap` guard still fires), so that's perf, not correctness.
  - **`fg.mean` / `fg.invnorm` and `G` (src:1317, 1361-1363, 2213).** Sums are zero-safe **but the denominator is not the same number.** Today `G` = count of frames *touched by any fragment's real point* (src:1312-1317). Under "the grid IS the window's frame sequence," the natural `G'` = `F`, the window's frame count. Any frame whose peaks are all sub-noise (`tp.frame_live[f] == 0`, src:795) is untouched, so `G' > G` in general, and since `pmean = psum/G`, `fg.mean = sum/G`, and the Pearson at src:2213 all divide by `G`, **every correlation in the window changes**. Fix: keep `G = |{f : some trace has a non-zero at f}|` — one pass over the arena per window. The doc does not mention this anywhere. This is the single most damaging omission: it's not an edge case, it's the denominator of the main score.
  - **`nearest_slot` landing slots (src:1323-1340, 2119).** Today's table maps to the nearest *used* frame within `delta_rt`, ties later. If the rebuilt table maps to the nearest *window* frame (used or not), precursor intensity lands on slots no fragment touches → `touched`/`psum`/`psumsq` change → `c` changes. The used-frame set and the ties-to-later rule must survive the renumbering.
  - **Sample-rate test (src:923-931).** In the detector, before any span exists. Unaffected. The doc is right.
  - **`atrousLevels` (src:1279-1297).** Breaks twice. (i) `tr.np() < 5` becomes `len < 5`, admitting traces that today return 0 levels. (ii) The median `dt` is computed over consecutive *points*; dense padding makes every `dt` exactly one MS1-frame step, deleting the gap information the function exists to measure ("a valley-split trace can carry gaps", src:1277-1278). The level count `j` changes → the smoothed precursor changes → every correlation against it changes. Only live when `trace:wavelet_smooth > 0` (default off), but "off by default" is not "pure representation."
  - **Wavelet smoother input (src:2107-2111).** `raw_i` over a dense span feeds zeros to `atrousSmooth` as if they were data; the B3 filter support crosses gaps and produces different values at *every* point, not just the gaps. This cannot be fixed by skipping — the smoother has no notion of missing. To reproduce today you must compact to the non-zero subsequence, smooth that, and scatter back. That is an O(len) compaction per precursor per window, or a non-zero index list per MS1 trace — either way, a cost the doc's "two sequential streams, no gather" story hides.
  - **FWHM (src:2647-2666 and `fwhm_of` 2843-2866).** The walk stops at the first point `<= half`. A gap (zero) adjacent to the apex triggers an immediate crossing and a fabricated tiny width; worse, the *truncated-peak exclusion* (a peak that never falls to half max is excluded, src:2640-2642) inverts — any trace with an interior gap now "falls to half" and is *included* with a wrong width. `ms1_fwhm_med` feeds `ms2_split` via `trace:split_valleys_fwhm` (src:2700-2707) and `wl_scale_` (src:2687-2691) — so this propagates into the splitter and the smoother, i.e. into the trace set itself. Fix: walk the non-zero subsequence.
  - **`xicCorr` (src:1751-1763).** Today `m` counts frames where *both* traces have points. The doc's "aligned dot product over the interval overlap" counts frames where one side is a padding zero: `sx += x; sy += 0; sxy += 0; ++m` — `cov`, `vx`, and `m` all change, and with them every isotope co-elution score in `inferPrecursors_` (src:1962), hence the precursor set. Fix: count only frames where both arena values are non-zero (intensities are strictly positive by construction — membership is `> noise`, src:795 — so `!= 0` ≡ present).

  So: of the ten statistics named, **five are zero-safe as claimed** (`dot`, `fsum`/`fsumsq` sums, `mean`/`invnorm` sums, sample-rate, scorer `overlap` *given the explicit skip*), and **five change value unless fixed** (`overlap` without the skip, `var_support_`'s `n`, `G`, `atrousLevels` + smoother input, FWHM, `xicCorr`'s `m` — that's six counting `G`). "Every consumer already skips zero intensities" (doc §2) is not true of the code I read.

  ## 3. Window-local vs global frames

  There are exactly three cross-frame-space alignments in the file, and no cross-*window* alignment at all (fragments live in exactly one window, keyed at src:2425-2427/2552):

  - **Precursor↔fragment: `fg.nearest_slot[p_tr.xi[pi]]` (src:2119).** Today: global axis index → grid slot, one table over 33,553 global frames. Under the redesign the precursor's points are MS1-sequence-local and slots are window-MS2-local, so the table must be **per window, keyed by the MS1 map's frame index (1,343 entries), valued in window-local MS2 frames**, built by matching RTs within `delta_rt`, ties later, over the *used* frames (§2). The doc's "indexed by window-local frame — ~1,400 entries" is ambiguous to the point of being wrong if read literally: the *keys* are MS1-local (the ~1,343 MS1 frames, plausibly the "~1,400"), the *values* are window-local. If someone indexes it by the window's own MS2 frames, every precursor scatters onto garbage. Spell it out.
  - **Isotope partners: `xicCorr(ms1[i], ms1[k])` (src:1962).** Both operands are MS1 traces in the MS1 sequence — same frame space, interval overlap works. Only the zero-skip of §2 is needed. MS1 traces are shared read-only across all 24 window tasks; the MS1 frame table (`rt_index` only) is built once. Fine.
  - **Precursor inference otherwise reads scalars only** (`mz/rt/im/intensity`, src:1778-1913, 2045-2080) — no frame arithmetic. `detectTracesInteger_`'s span test (src:926) and `splitIntegerTraces`'s `b_of_rt` (src:993-994) already go through `sl.rt_index`/`sl.b` and are trivially convertible.

  So window-local indexing breaks nothing *structurally* — but the doc should name the one table that crosses spaces and state its key/value spaces precisely.

  ## 4. The arena and the task pool

  The current sequencing is: band `taskloop` (src:3188-3195, implicit join) → serial concat (3196-3199) → `splitIntegerTraces` chunked `taskloop` (999-1043) → sort (3227) → `buildFragGrid` `taskloop` (1348) → scoring `taskloop` (3335). The redesign slots into that skeleton safely **if and only if** it preserves this order:

  1. Band tasks append to band-private arenas. Safe: one thread per band (`detectTracesInteger_` is serial within a band), offsets are indices so reallocation is harmless, no cross-band reader exists.
  2. **Taskloop join → serial concat + rebase, before anything else.** Nothing may read `off` between a band task's end and the rebase. Today nothing does — but note `traceDigest_` (src:624-635) reads `t.intensity`, which under the redesign is `arena[off + apex]`: any SPEXTRACTOR_DET digest must run post-rebase (or per-band against the band arena). The doc's risk row states the rebase but not the "no reader before it" invariant.
  3. **The split's chunked taskloop runs after concat** (as today, src:3202) and — this is the payoff — with aliasing children it performs **zero arena writes**: children are `(parent.off + a, b - a)` records appended to chunk-private `parts[ci]` (src:997, 1030). No shared-arena append race can exist because there are no appends. Parent ranges stay live (append-only arena), which is a *change* from today's chunk-wise `freeProfile()` (src:1023-1024): peak arena occupancy during the split is the full window's spans, not a shrinking set. That's still strictly less than today's xi/xv/xt + EPD list coexistence, but the ledger accounting (`MEM_TRACES` adds/subs at src:954, 1023, 1040) must be rewritten to match, or the 12 GB falsifier measurement will be nonsense.
  4. **The scorer's `taskloop` (src:3335) is read-only on the arena**, and the arena cannot grow after step 3 — nothing allocates trace storage after the split. The one thing to *not* do is compact the arena after the split (dropping parent-only spans): that would be a second rebase racing with nothing yet, but it must wait for the split's join and rebase every child — flag it as a deliberate non-optimization.

  One hazard the doc misses entirely: `buildFragGrid`'s `taskloop` (src:1348-1367) today *frees* each fragment's XIC as it resamples. Under the redesign there is no grid build and nothing to free — but the **frag sort by `im` (src:3227) permutes the trace vector after the arena is laid out**, which is fine for correctness (`off` travels with the struct) and kills any "arena order == trace order" invariant (see §6).

  The exact safe sequencing, stated: band taskloop join → concat+rebase (serial) → split taskloop (arena read-only, children alias) → join → sort → mean/invnorm pass (arena read-only) → scoring taskloop (arena read-only). Every stage barrier already exists in today's code; the redesign must not remove any of them.

  ## 5. The arithmetic

  Today's number checks out: 120 B struct + 48 B malloc headers + 12 × 10.7 = **296 B/trace**. The redesign's typical case checks out too: 18 (really 20 — the struct is 4-aligned: 3×4 + 3×2 = 18 → `sizeof` 20) + 4 × 14 = **74-76 B/trace** at a plausible typical sample rate of ~0.76 (10.7 real / 14 spanned).

  **The "at most 2x padding" bound is right at the default, but only at the default, and the doc states it as a theorem.** The detector accepts when `size / (visited − trailing misses) >= msr` (src:929-931). Since `adjusted = visited − trailing_misses = span + trailing_empty_frames ≥ span` (trailing *empty* frames are counted in `scans` but are not misses, src:903, 916-919), the rule implies `span ≤ size / msr`. At `msr = 0.5`: `span ≤ 2 × 10.7 = 21.4` → worst case **18 + 86 ≈ 104 B/trace** — still 2.9× better than 296. But `msr` is a user parameter (`trace:ms2_min_sample_rate`, src:1441 — and this repo has benchmarked 0.3 and 0.1): at 0.3 the bound is 3.3× (161 B/trace), at 0.1 it is **10× → 446 B/trace, worse than today**. The bound is `span ≤ size/msr`, full stop; the doc should print that, not "at most 2x."

  Two more qualifications: (i) the 2× bound applies to *detector output*; EPD children are not subject to any sample-rate rule, and a child can in principle have arbitrarily bad density within its sub-span — the aggregate arena stays bounded only *because* children alias the parent's range instead of copying (a point in the design's favor it should make explicitly). (ii) The 35.6 GB → 9 GB extrapolation holds only because points/trace and trace count are representation-invariant — which is exactly what §2 and §7 put in doubt; if the digest gate forces the fixes of §2, the arithmetic survives.

  ## 6. What else should go

  - **`off` (4 B) — keep it.** Prefix-sum derivation requires arena order == trace order, which fails twice: EPD children *alias* parent ranges (nothing is appended for them), and the frag sort by `im` (src:3227) permutes traces after layout. Even with a copy-in-final-order layout, random access by `fi`/`trace_idx` needs an O(1) prefix, i.e. the array you just deleted. 4 B × 7.5e6 = 30 MB/window is not where the 35 GB lives.
  - **`imq` for MS2 — cannot be dropped.** IM is the primary slice: `lower_bound`/`upper_bound` on `frag_im` (src:2135-2136) defines the candidate set, `dim` feeds `weighted_` (src:2368), and `im` is a sort key (src:3228). Dropping it deletes the gate, not the memory. **What should be challenged is not its existence but its width** — see §7: a uint16 quantization of the *centroid* is a behavior change.
  - **`apex` — keep it, the "two places" count is wrong.** The apex enters `rt`, `b`, `intensity`, and `mz` accessors, and those are read by the frag canonical sort (four fields × O(n log n) comparisons, src:3227-3232), by the scorer's emit path (src:2387-2388, 3295-3296, 3406-3407), and by export. A scan of `len` floats per access inside a sort comparator is real work for 2 B/trace (15 MB/window). Non-negotiable at this price.

  ## 7. The falsifier: byte-identical is not achievable as designed

  First, the good news: **floating-point evaluation order is not the problem.** Skipping a zero entry and adding `+0.0` are bit-identical for these sums (all values finite and non-negative; ascending-frame order is preserved in the arena). With the §2 fixes, every sum lands on the same value.

  The problem is that three accessor lines in the doc's §3 table **redefine values that are not derivable from what the new struct stores**:

  1. **`mz` (integer path).** src:950: `t.mz = cmz` — the *running iterative weighted centroid* from the extension walk (`iwm` updates in interleaved down/up order, src:910). It is detector state, not a function of the stored profile; `mzOf(tof, b)` is the *apex bin's* calibrated m/z, a different number. Consumers that will see the new value: the `[M-7]` precursor-peak exclusion `fabs(f.mz - pc.mono_mz) < 0.01` (src:2148), `drop_prec_iso` (src:2154), and the frag canonical sort key (src:3229) whose tie-breaks propagate into `assembleFromList_`'s index tie-break (src:2328). Borderline gate flips at ~1e10 comparisons are a certainty, not a risk.
  2. **`im`.** src:952: `t.im = IM_LO + cim/IM_Q` with `cim` a *double* running centroid of quantized values. The redesign stores `imq` as `uint16` — that re-quantizes the centroid, shifting every trace's IM by up to half a quantum (~1.07e-5). Consumers: the IM slice bounds (src:2135-2136) — a flip at the 0.01 boundary adds or removes a candidate; the sort; the isotope-partner IM gate (src:1807); and **`prec.setDriftTime(pc.im)` (src:2344) — the value is exported**, so the emitted mzML differs on essentially every spectrum even if membership is untouched.
  3. **`mz`/`rt`/`im` (OpenMS path — which is ALL of MS1).** MS1 always goes through `detectTraces_` (src:2628), whose traces have `tof = 0` and `t.mz` = the *picked* peak m/z (src:304), `t.rt` = `getCentroidRT()` (src:307 — a centroid, **not on the frame grid**), `t.im` = `getCentroidIM()`. None of these is reconstructible from `(frame0, len, tof, imq)` — for MS1 there is no bin at all. `pc.rt` becomes the emitted spectrum's RT (src:2336) and enters every RT gate; `ms1[j].mz` drives partner search windows and the `ms1[j].mz == best_mono` identity test (src:1913, 2014). Converting MS1 traces to the new struct as the doc intends ("one PeakSlab-like frame table for the MS1 map") changes the emitted file *by construction*.

  So the byte-identical digest gate fails by construction, before any bug is written — and perversely, `traceDigest_` (src:624-635, which hashes `mz`/`rt`/`intensity`) will "catch" this immediately and be unactionable, because the difference is the design, not a defect.

  **The correct gate is two-tier:**

  - **Hard gate (the actual representation claim):** a canonical digest over `(frame0, len, tof, b[frame0+apex], arena[off..off+len))` per trace, plus exported-peak m/z/intensity pairs (which come from `tof`/`b` via `exportMz_`, src:2302-2307, and so are representation-invariant on the integer path). This must be **byte-identical**, and it legitimately can be — given the §2 zero-semantics fixes, the `G = |used|` fix, the nearest-used-slot mapping, and the transient per-point bin arena through the split that reproduces `tofOf(mzOf(xt[a+apex], b), b)` exactly.
  - **Soft gate (the accessor redefinitions):** emitted spectrum *count* identical; precursor RT/IM within stated quanta (half a quantum IM; apex-frame vs centroid RT); and the repo's standing end-to-end gate — identified peptides at fixed FDR within the measured ~0.7% run-to-run wobble (documented at src:2718-2727), on dataset D, both engines.

  The alternative that keeps the doc's byte-identical ambition intact: **keep the three cached doubles (24 B) for gate-facing scalars** and delete only `xi`/`xv`/`xt` and the three mallocs (≈ 250 of the 296 B). That version can be bit-identical; the doc's 18 B version cannot. The honest choice is between "4× smaller, digest-stable within quanta" and "3.2× smaller, byte-identical" — the doc currently promises 4× *and* byte-identical, and it can't have both.

  ## Verdict

  **Not sound as written; sound after surgery.** The arena, the FragGrid elimination, the sub-span children, and the concurrency sequencing are all correct and worth doing. But the doc's central factual claims fail in three places: the accessor table's "everything derivable" (§3 table, doc lines 59-68) is false for `mz`/`im`/`rt`; the "every consumer already skips zeros" evidence (doc line 39) is false of `G`, `var_support_`'s `n`, `xicCorr`, `atrousLevels`, the smoother input, and the FWHM walk; and the "at most 2× padding" bound is parameter-dependent, not a theorem.

  **The single riskiest line in the refactor** is the accessor `mz → tofAxis().mzOf(tof, sl.b[frame0 + apex])` (doc line 62) replacing `t.mz = cmz` (src:950): it silently redefines the integer detector's m/z from the running centroid to the apex bin's calibration, it feeds a gate (`fabs(f.mz - pc.mono_mz) < 0.01`, src:2148) that fires ~1e10 times per run, and the doc presents it as a cost note ("one calibration call") rather than the semantic change it is. Runner-up: the deletion of `t.xt.push_back(...)` (src:945) without a bit-exact plan for the child apex bin — the `[adv-review vibe 2026-09-03]` comment at src:247-251 documents that this field exists precisely because getting it wrong systematically biases every split trace's reported m/z, and the fix that bias cost a review cycle once already.
