  ## 4. Why the reference implementation is 3.1x cheaper in CPU

  Not implementation — algorithm. The gap lives in work volume, in this order:

  1. **It traces summed frames; you trace raw ones.** the reference implementation sums adjacent cycles into a composite (m/z × 1/K0) matrix *before* peak picking (documented in your own `aggregateFrames_` header, :290-303). Point volume into its trace-equivalent stage drops ~Nx and S/N rises ~√N, so far fewer noise fragments survive. You centroid every raw frame and trace at noise 10 (:786, `ms2_min_length_sec` 0), producing up to 8.5M fragment traces in one window. Trace (48.7%) and score (46.1%) both scale with trace count — score superlinearly via candidate pairs.
  2. **Your m/z tracer is superlinear in local density; theirs is a matrix extraction.** Your own sweep proves it: banding cuts *total* trace CPU 11,168 → 5,378 → 2,972 s across 5/12/24 bands (:2379-2383). A linear algorithm shows flat CPU under partitioning; halving the CPU by halving the band means MassTraceDetection's per-apex candidate scan is doing quadratic-ish redundant work. the reference implementation never pays it.
  3. **Correlation candidate volume.** You linearly scan the whole IM band per precursor (:1500-1502) and RT-gate *after* (:1505); with ~932k hypotheses (≈40% guessed singletons, :2082-2083) × an IM band holding 5-15% of 8.5M fragments, the scan itself is ~10¹⁰-10¹¹ element visits per window before a single dot product — the dot only runs for the ~0.3% passing the 3 s RT gate. the reference implementation correlates per detected feature against intensity-ranked fragment sets with a pre-smoothed precursor profile: fewer, cheaper pairs.
  4. **Duplicate edge work**: 12 bands × 20 ppm halo (:975) + the 1.000 Da window overlap → every boundary ion traced and scored twice (~14% combined).

  Output volume is equal (863k vs 872k spectra), so the extra 56k CPU-s bought nothing in quantity. Plainly: **the algorithm does roughly 3x more work by design, and no scheduling recovers that.** What tuning *can* recover is the 29% idle plus the redundant-work items 2 and 3 — maybe down to ~1.4-1.9x CPU. Parity requires item 1 (frame summing, fewer traces), which changes output.
