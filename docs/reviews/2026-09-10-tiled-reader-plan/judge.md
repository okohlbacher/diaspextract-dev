# Tiled pass-2 reader: judged implementation plan (workflow wf_1d897d68, 2 plans x 3 refuters + judge)

## Chosen
Graft: the "clean" plan's ORDER and structure (frozen tables -> tile loop on a resident source with carry/deferral and per-tile streamed write, gated G1-resident BEFORE any reader code -> band-partition re-pin -> the .d reader -> mzPeak -> pipeline -> hardening), with the "minimal" plan's mechanics where they are smaller and equally exact: Config-range entry point + per-tile re-open instead of a public DIAFrameSource class (needs a pimpl: openTimsDataHandle is file-static, FrameAggregator is in an anonymous namespace), the window body kept as the existing lambda with added captures instead of a WindowState refactor, the tof index on the cell's own extremes. Four things neither plan had right are settled from the code: (1) the .d frozen frame table is EXPORTED BY THE LOADER (its own doubles, group ids and windows), not re-read from sqlite in either form; (2) padding is a lockstep APPEND during the hand-off, not an insert and not an assert-and-refuse; (3) the band partition is a G-class re-pin, not D-class; (4) the carry is transitive for free (filter over all of frag_traces), so no pitch >= 2*delta_rt constraint exists. The range entry point is folded into the regenerated calibration patch (scripts/regen_openms_patch.sh diffs .orig vs file into ONE BrukerTimsFile patch anyway; a separate 5th file named *dia-range* sorts before *mz-calibration* in apply_openms_patches.sh's glob and fails).

## Reader decision
.d: an OpenMS patch, not tool-side iteration -- but the SMALL form: `BrukerTimsFile::Config::dia_ms2_rt_lo/hi` filtering each group's `frame_ids` by `handle->get_frame(fid).time` before the 256-frame batch loop (calibration patch hunk @@ +1646, ~30 lines), plus the loader EXPORTING its own per-group frame table and window table (`lastDIAFrameTable()` / `lastDIAWindows()`, ~25 lines, the `lastMzCalibration()` pattern). Not a public `DIAFrameSource` class: everything it would own is .cpp-local (openTimsDataHandle is `static` at .cpp:929, FrameAggregator sits in the anonymous namespace :395-907, opentims headers are only included by the .cpp), so it needs a pimpl and ~200 patch lines for what the Config field does in 30; the handle is re-opened per tile (sqlite reads of 72k Frames rows via sqlite3_exec + 134k DiaFrameMsMsInfo rows + T1 + windows, est. 0.3-1 s, x13 on TNBC), output-neutral, measured by the tool-side timer, escalated to a persistent handle only if > 2 s. Not a tool-side opentims reader: it would duplicate the tiered calibration :929-1150 that spx:mz_calibration vouches for. Why the export and not a tool-side sqlite table (either plan's form): opentims fills `TimsFrame::time` with `atof()` of sqlite3_exec's TEXT rendering ("%!.15g"; opentims.cpp:61-79, :245-254, :281-289), so `sqlite3_column_double` does not bit-match in general, and the rt_index-based equality check both plans proposed is blind to an ulp (rtIndex :253-256 snaps to the nearest axis value) while nearest_local ties (:1710-1711) and the axis's sort/unique are not; the export gives the spectra's own doubles, group ids and windows by construction and makes the old-format-tdf fallback (.cpp:769-800) a non-issue. The patch is delivered by regenerating the existing calibration patch (scripts/regen_openms_patch.sh diffs .orig vs file into one BrukerTimsFile patch); a separate `openms-brukertims-dia-range.patch` would sort before `openms-brukertims-mz-calibration.patch` in apply_openms_patches.sh's `for p in patches/*.patch` and exit 1. Pass 1 = load_ms1=true with an empty MS2 range (lo=+inf, hi=-inf: every group's sel is empty, `ms1_to_emit` unchanged, the aggregated ms1_n_neighbors path included); pass 2 per tile = load_ms1=false (BrukerTimsFile.h:55, honoured at .cpp:1397) + [T_a, T_b) with -inf/+inf ends. Frame set per cell = the whole-run loader's restricted to the range (the per-frame body is untouched: num_peaks==0 skip, IM slice, `!spec.empty()`, group-major order); picked bits per-frame pure (0b); factors per frame id from the tool's TdfLoad read. Padding: a window frame the loader never hands over (empty IM slice) is appended EMPTY in lockstep during the hand-off, so the slab's frame sequence IS the frozen table's slice in every mode (zero pads on D/TNBC; counted; an e2e fixture exercises it). mzPeak: `MzPeakFrameSource` = the metadata sweep computed ONCE and cached (otherwise LOAD multiplies by K: the 72k metadata() calls are the bulk of mzPeak's 131-s LOAD on D) + `run(ids)` over the ms2 ids in range with the thread-local Index reused across tiles, tail chunks sized ceil(n/nthr). mzML: the whole picked run stays resident (no random access) and `ResidentFrameSource::readTile = sliceFrames` per window -- the same interface the two real readers implement, which is what lets the e2e fixture drive the tile loop, and whole-run mode = one tile of it by std::move. LOAD scaling: tiles PARTITION the MS2 frames (no halo), so every MS2 frame is decoded and picked exactly once over the run and every MS1 frame once in pass 1; the only per-tile costs are K handle opens (.d), K x 14 partial 256-frame decode batches (a 113-frame tail still fills 100 threads once), K partial pick batches (~50 ms each), and on mzPeak the partial 1,200-frame batch unless the tail chunk is resized.
