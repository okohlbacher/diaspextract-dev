• Adversarial review of the two changes, worked solely from the inlined text. Findings are numbered by severity; each has location, scenario, and fix. Areas where I found nothing are stated explicitly at the end.

  ## Findings

  **1. `__cpp_lib_to_chars` does not detect floating-point `from_chars` — the libc++ fallback is dead code on the platform it was written for, and the taken branch can fail to compile.**
  Location: `src/DnoiseMs1.h`, `detail::parseF64` (`#if defined(__cpp_lib_to_chars)` … `#else` istringstream), and the comment "libc++ does not define `__cpp_lib_to_chars`".
  That comment is wrong. `__cpp_lib_to_chars` (201611L) is defined by every implementation with the *integer* `<charconv>` facility — libstdc++ since GCC 8, libc++ for years — and no distinct macro signals the floating-point overloads. Consequences:
  - On libc++/macOS the `#if` branch is taken, never the istringstream fallback. Where libc++'s FP `from_chars` is absent or availability-gated (the header itself says macOS 26), this is a *compile error* or an availability diagnostic, not a fallback — precisely where the fallback was intended to run.
  - Same break on GCC 8–10 (macro defined, FP overload added in GCC 11).
  So the portability CI claim ("both paths") is illusory: the `#else` path is only reached on a library that defines neither — which barely exists. Fix: use a configure-time probe (`check_cxx_source_compiles` calling `std::from_chars(first, last, double&)`) and define e.g. `SPX_DNOISE_HAS_FP_FROM_CHARS`, or at minimum `#if defined(__cpp_lib_to_chars) && !defined(_LIBCPP_VERSION)`. Compile both variants in CI.

  **2. The prune's identity breaks on any MS1 spectrum that is not already m/z-sorted at load.**
  Location: `Ms1Prune::frame` — `s.sortByPosition()` runs *before* the stride-97 sample is written.
  The pre-change code sampled the map *as stored* in `detectTraces_` (`sample.push_back(s[i].getMZ())` over the raw order). For an unsorted spectrum, the prune now samples a different multiset of positions → different quantile edges → different bands → different output, contradicting "OUTPUT-IDENTICAL". Reachability: the resident mzML path skips `pickIMCluster` when `s.getIMPeakType() == IM_CENTROIDED` (see the pick loop: `if (s.getIMPeakType() != IMPeakType::IM_CENTROIDED) picker.pickIMCluster(s)`), and nothing in mzML guarantees m/z order — so an already-centroided, unsorted MS1 spectrum reaches `frame()` unsorted. The same skip exists in the streaming `flush_`. There is a second-order effect too: post-prune the spectrum is sorted, so the band builder takes the `src_sorted` lower_bound path instead of the old scan fallback — same peaks, different in-spectrum order handed to MassTraceDetection.
  Fix: in `frame()`, if `!s.isSorted()`, write the sample but skip the prune entirely for that spectrum (reproduces the legacy behavior bit for bit); or sample from the original order before sorting *and* prove MassTraceDetection is in-spectrum-order-independent. The e2e fixture writes sorted peaks, so check 19 cannot see this; add a scrambled-order mzML arm.

  **3. The contraction guards are unproven exactly where they are the only guard.**
  Location: `src/DnoiseMs1.h` (`#pragma GCC optimize("fp-contract=off")`, `#pragma clang fp contract(off)`, the `volatile`), `CMakeLists.txt` (`SPX_NO_FP_CONTRACT`).
  - GCC documents the `optimize` attribute/pragma as a debugging aid, not production-suitable; per-function `-f` options through it have a history of being rejected-with-warning or silently misapplied. If the pragma no-ops, only the `volatile` remains.
  - The CMake flag covers GNU/Clang/AppleClang for the three named targets only. The documented in-tree OpenMS build and MSVC/clang-cl get *neither* flag; `#pragma clang fp contract(off)` is clang-only; MSVC contracts under `/fp:fast`+`/arch:AVX2`. On all of those the `volatile` is the sole guard.
  - The stated validation ("unit test fails with the guards removed") was evidently run where the flag, the pragma, and the volatile were all present together, so the volatile's sufficiency in isolation is asserted, not measured.
  The exposure is genuinely small — auditing the builder, the only `a*b+c` shape is `im0/im1 = scan_intercept + scan_slope*scan` (the `t0/t1` chains are sub/div/sqrt and cannot contract) — so a working volatile is sufficient. Fix: add one CI job that compiles `test_dnoise_ms1.cpp` with GCC `-O3 -march=x86-64-v3` (or `-mfma`) *without* `-ffp-contract=off` and with the pragma region removed, proving the volatile alone pins D's 24 boxes; and decide whether the GCC pragma is kept (verify it is accepted, not warned-away, on the oldest supported GCC).

  **4. `Ms1WindowGate::fromBoxes` folds an entirely out-of-range box onto the last scan instead of dropping it.**
  Location: `fromBoxes` — `const std::uint32_t lo = std::min(b.scan_lo, num_scans - 1), hi = std::min(b.scan_hi, num_scans - 1);`.
  The builder clamps `scan_hi` but never `scan_lo`. A window row with `scan_num_begin > num_scans - 1` (method/acquisition mismatch: `DiaFrameMsMsWindows` written for more scans than `MAX(Frames.NumScans)`, or the u32-wrapped `i64 as u32` cast producing a huge begin) yields `lo == hi == num_scans - 1`, and the box's TOF interval is *added to the last real scan* — points there pass the gate that dnoise (if it skips such boxes) would reject. The header pins the `tof_hi < tof_lo` skip but not this case, and the fuzzing was "random gates" against a transliteration of the Rust, which shares the assumption rather than testing the binary. Fix: check dnoise v0.1.0's `DiaMs1Gate` construction for this exact case against the binary with a doctored window table; if dnoise drops the box, add `if (b.scan_lo >= num_scans) continue;`; either way pin it in `tests/test_dnoise_ms1.cpp`.

  **5. The streaming-side prune has no in-repo end-to-end coverage.**
  Location: `PickCompactConsumer::flush_` (`if (ms1_prune && ms1_prune->on) ms1_prune->batch(ms1_buf_, …)`) and the `ms1_prune.frames != ms1_map.size()` precondition.
  Check 19's fixture is synthetic mzML, which is forced through the *resident* path (`ms1_prune.batch(exp.getSpectra(), …)`); the streaming source requires a Bruker `.d`. So the consumer branch, the cross-batch `sample` offset accumulation, and the frames/sample accounting under tiling are pinned only by the dataset-D digest (8c1b047f) outside the repo. A regression that only manifests across `flush_` batch boundaries (e.g. an offset or counting bug) would pass `test_spextractor.py`. Fix: extend the mzPeak/tdf fixture machinery already used by check 18 (`synth_tdf` + `SPEXTRACTOR_MZPEAK_TDF`) to drive one streamed prune on/off comparison, or state explicitly that streaming-mode prune correctness is harness-only.

  **6. `select()` releasing capacity is asserted, not shown — and the ledger model bakes in the assumption.**
  Location: `Ms1Prune::frame` comment "into right-sized buffers"; the ledger line `ledAdd_(LC_MS1MAP, mb)` with `mb = s.size() * 20`; the log's `kept * 20` MB figure.
  If OpenMS `MSSpectrum::select` compacts in place (remove+resize) rather than reallocating, capacity — ~81% of the pruned map at 25 B/peak of slack — stays resident and the ledger's 20 B/peak model understates the MS1 map after the prune. The measured 31.82 → 26.49 GB peak is consistent with release but doesn't prove per-spectrum right-sizing (the peak may be set elsewhere). Fix: verify `select`'s implementation once and adjust the comment; if it does not shrink, `MSSpectrum(std::move-selected)).swap(s)` or charge the ledger on capacity.

  **7. `parseF64` is a real, if deliberate, divergence from dnoise on corrupt metadata — the "bit-identical" contract needs a qualifier.**
  Location: `parseF64` doc comment: "inf, nan and out-of-range literals, which Rust accepts, are refused."
  Rust's `f64::from_str` accepts `inf`, `infinity`, `nan` (any case) and overflows to ±inf (`"1e999"`). dnoise would build a garbage gate and proceed; the port sets `GateBuild.error` and refuses the run. On any real timsTOF file these values never occur, and refusing is defensible — but the stated contract is "bit-identity with dnoise", and this is a case where the port *refuses a run dnoise completes*. Fix: one sentence in the header contract limiting identity to finite metadata; no code change needed.

  **8. `reach()` in the prune is FMA-contractible, on build paths without the CMake flag.**
  Location: `Ms1Prune::frame` — `return x <= m + hop * m;`.
  `m + hop*m` is exactly the `a*b+c` shape; `spextractor.cpp` gets `-ffp-contract=off` only for the CMake GNU/Clang build, not the in-tree OpenMS build or MSVC. Here it is benign: the membership proof has a factor-2 margin (`hi - lo >= 2h·lo/(1-h)` vs a hop of `h·m`), and one ulp of `hop·m` cannot cross it; and the computation is identical in prune-on and prune-off builds under the same flags, so it cannot break the *A/B* identity, only the theoretical exactness of the bound. No fix required; noting it because finding 3's gap means this file too compiles unguarded somewhere. If you want it airtight, parenthesize through a volatile or compute `hop * m` once per spectrum.

  **9. The dnoise unit test is only wired into the `SPEXTRACTOR_TESTS_ONLY` build.**
  Location: `CMakeLists.txt` — `add_executable(test_dnoise_ms1 …)` and `add_test(NAME dnoise_ms1 …)` appear only inside the `if(SPEXTRACTOR_TESTS_ONLY)` branch, which then `return()`s.
  The primary (OpenMS) build — the one that ships the binary and runs on the cluster — never compiles `tests/test_dnoise_ms1.cpp`, so the pinned D/TNBC gate boxes and the guard-removal tripwire are exercised only in portability CI. A header edit that moves the boxes ships green through the main build. Fix: register the same test in the full build path (it is dependency-free per the header comment, so nothing blocks this).

  ## Areas checked with nothing found

  - **Streak-filter equivalence shortcuts** (claim 1): the two-pointer window is sound because block TOF values are nondecreasing and so are the saturated `[c-w, c+w]` bounds; the `n_occupied < min_feature_length` skip is exact (a run holds at most `n_occupied` occupied scans); the early stop on a no-removal pass is a true fixed point of a deterministic pass; the gap rule (`step > max_internal_gap + 1`), occupied-count-vs-span rule, span-sum floor, and TOF-`c`-only marking all match the stated semantics, including zero-intensity points kept by span.
  - **Halo** (claim 4): whole-column exclusion (`*q != ti`), tie-keeping `>=`, `best == 0` keeps, clamped scan window, saturated TOF window, and simultaneous judgement (marks applied via `compact` only after all decisions) all match the spec. The counting sort by scan preserves per-scan TOF order, so the `lower_bound` per scan row is valid. No FP hazard: the ratio compare is a lone multiply.
  - **Radix sort**: digit loop covers bits 0–32 whenever `max_tof >> 22 != 0`; stability is irrelevant to results as claimed (sums are u64-exact, halo is a max). No counterexample found.
  - **Integer casts/saturation**: `asU32` reproduces Rust `f as u32` including NaN→0 and the 2^32 cutoff; the `i64 as u32` window-row wrap is replicated; u64 window sums cannot overflow at `m < 2^32`; fmin/fmax NaN behavior matches Rust `f64::min/max`.
  - **Gate-on-survivors-only**: exact, since the gate is ANDed last and no earlier stage consults it.
  - **The prune's band-membership proof**: the reach-or-adjacent invariant holds (consecutive kept peaks are within `hop·m` or have no peaks between them), so a band range containing any unpruned peak contains a kept one, with ~2× margin over rounding; first/last anchors and the forced far-side keep close the gap cases; empty spectra (`(0+96)/97 == 0`, `select` skipped) behave identically to the old path. Edge-sample order is irrelevant because `detectTraces_` sorts the sample; the multiset is identical. Exactly-at-noise and NaN intensities match MassTraceDetection's `(double)intensity > noise` (both false), and such peaks still serve as m/z witnesses.
  - **Prune concurrency**: disjoint `sample` offsets computed serially, per-index `Counts`, named `omp critical` for the exception, rethrow outside the region, deterministic under `schedule(dynamic,1)`. Batch/thread/tile invariance holds; `bands == 1` is identical because MassTraceDetection filters sub-threshold peaks itself and the prune never removes a spectrum; the `!streamed` reset plus the `frames != ms1_map.size()` refusal fails loud rather than tracing on unaccountable edges. No path found where the map is pruned but edges come from the pruned map — the precondition check converts any missed route into an abort.
  - **Check 19 vacuity**: not vacuous — it asserts `wit > 0`, `picked > kept`, `at_noise == 3`, digest equality at bands 1/2/48, `[ms1-edges]` and band-count equality, and requires the no-witness control to change traces or band spectra at bands 2/48 (correctly exempting bands 1, where witnesses are unobservable). The only soft spot is that the `[det] MS1 band spectra` line compares per-band *counts*, not content — acceptable given MassTraceDetection reads only `> noise` peaks and the final digest is compared.
  - **`SPEXTRACTOR_TILE_TRIM` probe**: glibc-gated, serial point between tiles, opt-in, output-neutral; nothing wrong.

  The two findings I would block on are #1 (the portability fallback never engages where intended — a latent compile break, not a rounding risk) and #2 (the prune's "output-identical" claim is only proven for m/z-sorted input, and already-centroided mzML can violate that premise silently).
