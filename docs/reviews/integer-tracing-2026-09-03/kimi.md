  ## 1. The faithfulness claim is not credible — §3 describes a different algorithm than the one the tool runs

  The design's §3 ("that is what is reimplemented — not a new algorithm") misdescribes the OpenMS semantics in at least four load-bearing places. `detectTraces_` (src/DIAPseudoSpectra.cpp:1353-1371) never sets `trace_termination_criterion` or `reestimate_mt_sd`, so the tool runs OpenMS **defaults**: outlier termination, dynamic SD. What that means:

  **Differences that change which traces exist:**

  1. **Termination rule.** OpenMS default is `trace_termination_criterion="outlier"`: stop a direction after **5 consecutive** misses (`MassTraceDetection.cpp:41-43`, applied at 577/630). The per-direction `hits/visited < min_sample_rate` rule in §3 and in the draft (DIAPseudoSpectra.cpp:825) is OpenMS's *sample_rate* mode, which the tool does not run — and even that mode OpenMS implements with a 5-scan grace period and a **combined both-directions** hit/scans denominator (MassTraceDetection.cpp:582-593), not the draft's per-direction counter. Three different rules; the draft implements a fourth.
  2. **The final quality gate is missing entirely.** OpenMS *also* applies `min_sample_rate` at acceptance: `isTraceValid_` (MassTraceDetection.cpp:445-469) computes `trace.size() / (total_scans − trailing_consecutive_misses)` and rejects below threshold. The draft has no post-hoc quality check at all — it emits whatever survived extension. This is the project's "sole surviving MS2 trace-validity lever" (your own comment, line 1261, with a measured peptide loss when mis-set), and the draft silently deletes it.
  3. **`used` marking on invalid traces.** OpenMS marks peaks visited **only for traces that pass validity** (MassTraceDetection.cpp:653-660). The draft marks at take-time (line 829) and never unmarks when the trace fails the length check (lines 841, 851-852). Peaks of rejected traces are consumed, so they can neither re-seed nor join a neighboring trace. In dense regions this removes traces the OpenMS path would emit.
  4. **The tolerance window is not `mass_error_ppm`.** OpenMS initializes `ftl_sd = centroid·ppm/1e6` and accepts within **±3·ftl_sd** (MassTraceDetection.cpp:537, 301-302, 359-366) — i.e. 60 ppm at your 20 ppm setting — and with `reestimate_mt_sd=true` (the default you never override) replaces it with a robust running SD after the first points (`updateWeightedSDEstimateRobust`, lines 178-192, called at 438-441). The draft uses a fixed 1×ppm integer span (line 817). Early in a trace OpenMS's window is ~3× wider; later it is typically *narrower* than ppm. Membership differs on both ends.
  5. **Closest-then-reject vs closest-unused.** OpenMS picks the single closest peak inside the IM gate, and if that peak is already used, the frame counts as a **miss** (findBestPeak_ 288-343, isPeakAcceptable_ 381, run_ 552-566) — it does not fall through to the second-best peak. The draft's `pick()` (lines 788-795) takes the closest *unused* peak. In contested windows this changes both membership and the miss counters that drive termination.
  6. **IM gate pinned to the seed.** OpenMS maintains a running intensity-weighted IM centroid (processPeak_ 423-426) and gates each candidate against it. The draft gates against `scan0`, the seed's rank, fixed forever (lines 791, 804, 819). A trace whose mobility drifts over RT is followed by OpenMS and truncated by the draft.
  7. **Noise-floor membership.** OpenMS deletes peaks ≤ `noise_threshold_int_` from `work_exp` before tracing (MassTraceDetection.cpp:240-255), so they can never be trace members. The draft filters only the seed list (line 767); `pick()` has no intensity floor, so sub-noise peaks enter traces and drag the integer centroid.
  8. **Empty-frame accounting.** OpenMS does not bump the outlier counter for empty spectra (MassTraceDetection.cpp:549-572); the draft counts an empty frame as a miss toward the rate (lines 819-826). Windows with empty cycles terminate earlier.
  9. **Interleaved vs sequential directions.** OpenMS alternates one step down, one step up in a single loop, each side extending against the centroid built from *both* sides (run_ 540-648). The draft runs +1 to exhaustion, then −1 starting from the *final* +1 centroid (lines 812-839). The centroid path differs, so contested picks differ.

  **Order/reporting-only differences:** seed tie-breaks (draft's (tof,index) tie-break, line 770-774, is deterministic and fine — OpenMS's stable_sort + reverse iteration is not reproducible across implementations anyway); centroid rounded to integer bins each step (line 832); reported RT is the apex frame (line 860) vs OpenMS's intensity-weighted centroid RT (`toTrace` uses `getCentroidRT`) — small, but it shifts every `gate:delta_rt` comparison downstream; `mz_estimator="median"` is silently unsupported (line 857).

  Only item 9's second-order effects and the tie-breaks are "faithful but not bit-identical". Items 1-8 change the trace set. The design's claim "the comparison is about data structures, not about science" is false as drafted.

  ## 2. The mobility-axis derivation is false on this pipeline's own data

  The premise — "within one frame the distinct 1/K0 values ARE the scans" — holds for **raw** timsTOF frames. This tool never traces raw frames: `PickCompactConsumer::flush_` runs `picker.pickIMCluster(s)` at line 951 and *then* `compactify` at line 953. PeakPickerIM emits, per m/z-cluster, a **picked mobilogram centroid** (`PeakPickerIM.cpp:390`, `picked_trace[j].getMZ()` — a PeakPickerHiRes centroid, a grid-free float). So per frame the distinct `imq` values are picked feature centroids: their count scales with feature count (can approach the ~37k peaks/frame, far beyond the ~1000 TIMS scans), they are not drawn from a per-frame grid, and the same ion's centroid can swap rank order with a neighbor between frames. Ranking them recovers an ordinal of picked centroids, not the TIMS scan index. The design's own risk #4 ("if a converter has already merged or re-binned mobility") is not a hypothetical about some external converter — the tool's own picker does it, one line before the store is written.

  Two further problems even if you accept the ordinal:

  - **`scan_tol` is a worst-case density measure, not a tolerance.** `indexScans` (lines 704-711) sets the per-frame tolerance to the *maximum* count of distinct values inside `delta_im` anywhere on the ramp. On picked data, dense mobility regions (the peptide ridge) make `worst` large; the gate `|scan − scan0| ≤ scan_tol` then applies that large rank distance *everywhere*, including sparse regions where that many ranks spans far more than 0.01 1/K0. The IM gate becomes density-dependent and wider than `gate:delta_im` — a gate-semantics change, not a data-structure change.
  - The justification ("the calibrated value drifts frame to frame while the scan does not") is asserted, not measured. OpenMS applies per-frame TIMS calibration; if calibrated 1/K0 were not comparable across frames, the current OpenMS path's `ion_mobility_tolerance` on calibrated values would already be broken. Also the design text says sort *descending* ("1/K0 falls as scan number rises") while `indexScans` ranks ascending (line 702) — harmless for differences, but it shows the text wasn't checked against the code.

  **Cheap detection on real data:** (a) one SQLite query — `NumScans` from `analysis.tdf` (SQLiteCpp is already the `loadTofAxis` dependency, line 492) — against a per-frame count of distinct `imq`; if distinct ≈ peak count or ≫ NumScans, the premise is dead. (b) Grid test: for true scan-valued data, gaps between consecutive distinct values are multiples of a common per-frame quantum; picked centroids fail this immediately. (c) Cross-frame stability: histogram the same trace's member `imq` across frames — if stable, ranking buys nothing over gating on `imq` directly.

  **What to do when false:** drop the scan axis and gate on `|imq[k] − running_im_centroid| ≤ imq_tol` with a running centroid — that is today's OpenMS semantics in integer form, it costs the same, and it removes risk #4, the `scan_tol` widening, and the uint16 rank-overflow hazard (unguarded cast at line 702; picked frames can exceed 65,535 distinct values) in one move. Keep a scan axis only if a downstream consumer genuinely needs vendor scan numbers; none currently does.

  ## 3. The estimate is not honest — the two biggest claimed sources are already outside the number they're supposed to reduce

  The phase timers already answer "where does it come from", and the design doesn't use them. In the window loop, materialisation is timed separately (`t_mat`, lines 2918-2934) and `t_trace` starts *after* it (`_t2` at line 2940, accumulated at 3026), reported as separate lines (3233-3236). The 3,869 s = 90.9% is the **trace** line. Therefore:

  - **"No PeakMap materialisation" and "no double conversion" cannot deliver any of the 30-50% off t_trace** — that time was never in t_trace. They're a `t_mat` gain (and the S30 log already prints exactly how big that is; the design should quote it instead of estimating −1 to −2 GB of *memory*). Note also the prior reviewer in `docs/reviews/integer-tracing-2026-09-03/vibe.md` claims materialisation is 10-20% of the 90.9% and wants the falsifier at 25% — that premise is wrong given the timers.
  - **A large share of t_trace is ElutionPeakDetection, which the integer path currently skips.** `detectTraces_` runs `do_split` inside the timed region (lines 1378-1390, 1493 ff.); your own comment at 1485 records EPD-off saving ~28% wall (20:46 vs 28:40). The integer branch (2962-2993) never calls EPD, and there is no EPD adapter for `Trace`. So as drafted, `detector=integer` will show a t_trace drop of which a large fraction is *silently skipping valley splitting* — the exact merged-trace regression your comments at 1478-1484 and the +36.7%-peptides MS1 result (line 1257) document. A speedup that is mostly an unmeasured correctness cut.
  - What remains for layout: OpenMS's per-step search is *already* binary search + short window walk (`findBestPeak_`, MZBegin/MZEnd at 318-321), same asymptotics as the draft's `pick()`. The per-step win is bandwidth on the candidate walk (20→10 B/peak, no FDA indirection) plus object-overhead removal. The honest expectation for detector-proper is **15-25%, not 30-50% of t_trace**.

  The strongest evidence layout matters is already in your tree and the design doesn't cite it: at fixed total peaks and identical algorithm, trace CPU went 11,168 → 5,378 → 2,972 s across 5/12/24 bands (comment at 2944-2948) while *more* banding means *more* halo-duplicated peaks — i.e. cost scales with working set, not with work. That supports doing the refactor; it also predicts a ~2× density cut is worth roughly the 4→12-bands step (~30% of detector-proper), not 30-50% of the whole phase.

  **The falsifier is wrong in both directions.** As drafted, 15% off t_trace is reachable by the EPD omission alone (false pass); with EPD correctly retained in both paths and EPD's share at ~28% of t_trace, 15% off t_trace demands ~21% off detector-proper — plausible but not the floor you described. Restate it as: *t_trace with EPD retained in both paths falls ≥15%, t_mat ≈ 0, and peptide counts from both engines are within run-to-run noise.* And measure the EPD share first (one timer around `do_split`, or the existing `-trace:ms2_split_valleys 0` A/B): that single number sets the ceiling on what this refactor can ever return.

  ## 4. What this breaks — risks ranked, with symptoms

  1. **EPD silently skipped in the integer branch (not in the design's list).** Symptom: multi-modal merged traces return; precursors with wrong mono/charge; peptide count drops in the direction you already documented for splitting-off. Currently guaranteed to happen, not a risk.
  2. **Mobility-rank premise (design #4).** False on picked data (§2). Symptom: density-dependent IM gate, traces merged across mobility, fragments co-localizing to wrong precursors — peptide count moves both directions, silently.
  3. **`min_sample_rate` semantics (design #1) — worse than stated.** It's not "subtly different": different termination rule, missing final quality gate, different denominators (§1.1-1.2). Symptom: gappy fragment traces vanish or survive differently; the measured 8,865 → 8,735 sensitivity (line 1261) says this lever moves peptides at the percent level.
  4. **`used`-marking semantics (design #3 mis-scoped).** The race concern is handled (per-call `used`, line 776); the real issue is mark-at-take vs mark-if-valid (§1.3) plus closest-unused vs closest-then-reject (§1.5). Symptom: holes in trace coverage in dense m/z regions; fewer fragments for some precursors; no crash.
  5. **Tolerance window (not listed): fixed ppm vs ±3× reestimated SD (§1.4).** Symptom: trace m/z scatter distribution shifts; wide traces split, narrow ones absorb neighbors; isotope-envelope membership changes → charge/mono inference changes downstream.
  6. **Uniform TOF band edges (not listed).** The OpenMS path learned quantile banding because density varies orders of magnitude (comment 1402-1403); the integer branch partitions uniformly in bins (2976-2981) *and* rebuilds `frame_of`/`order` over the full slab per band (758-774) — 12 redundant full-slab sorts per window. Symptom: one band dominates; the promised speedup evaporates into scheduling.
  7. **Seeding determinism (design #2).** Adequately handled by the (tof, index) tie-break. Order-only. Lowest risk.
  8. Minor: below-noise members (§1.7), empty-frame termination (§1.8), apex-RT vs centroid-RT reporting, `median` estimator, `max_len=0` edge (OpenMS `>= 0.0` disables at −1; draft `> 0.0`), rank >65535 overflow.

  ## 5. Sequencing

  1. **Freeze and build.** Commit/stash the half-integrated draft; make `detector=integer` compile and fail closed on every unsupported combination (`agg>1`, `mz_estimator=median`, `max_len≥0`).
  2. **Build with SQLiteCpp so the flight-time axis actually executes.** Today `loadTofAxis` returns "built without SQLiteCpp" (line 527) and the integer path aborts at 2856 — the axis has never run, so nothing below is measurable until this is done. It's a build-flag change, not code.
  3. **Measure the ceiling before writing detector code.** Read `materialize` vs `trace` off the existing S30 phase table; add one timer around `do_split` (or rerun with `-trace:ms2_split_valleys 0`). If MTD-proper is under ~60% of t_trace, the 30-50% claim is arithmetically dead — stop or re-scope. This is also the single measurement that settles "extension search vs layout": combined with the band-CPU scaling you already have, an MTD-proper share ≫ EPD share + perf-stat LLC misses scaling with band count says layout is the lever; a large flat MTD-proper time at small working sets says it's the search.
  4. **Falsify the mobility premise (hours, §2 checks).** Almost certainly lands on "gate on imq directly" — which deletes the scan axis, `indexScans`, and risk #2 entirely.
  5. **Semantics-first implementation at bands=1, one window.** Mirror what the tool actually runs: outlier termination (5 consecutive misses), the `isTraceValid_` quality gate with trailing-miss adjustment, visited-only-if-valid, running IM centroid, noise-floor membership, closest-then-reject-if-used, centroid-RT reporting, and EPD on the output (an EPD-on-`Trace` adapter, or convert to `MassTrace` just for splitting — the conversion cost is per-trace, not per-peak). Deliberately decide the ±3σ-vs-fixed-ppm question as its own A/B with both engines, because it is a science change either way. Compare trace counts and length/scatter distributions against the OpenMS path on one window before any timing run.
  6. **Then performance:** slab + single-band integer vs openms wall at identical semantics; then banding with **quantile** TOF edges and a single partition pass (reuse the existing scheme, not uniform bins); then full S30 with both engines.

  **Skippable entirely:** the scan-rank mobility axis (step 4 will likely kill it); MS1 integer tracing (MS1 is ~4% of frames and separately banded — leave it on OpenMS); the `aggregateFrames_` port (fail closed when `agg>1`); `median` estimator and `max_trace_length` compatibility (fail loudly); the exact-partition drift-cap machinery — quantile edges with a generous halo are already exact in practice.

  **Verdict on worth:** provisionally worth doing — the banding CPU collapse at fixed peak count is real working-set evidence — but not at the stated number. With EPD retained, expect 15-25% off t_trace, i.e. roughly 4:50-6:00 → no, roughly 7:04 → ~6:00-6:30 wall, not 5:00. The one measurement that settles it: the `do_split` timer splitting MTD-proper from EPD inside the existing 3,869 s. If EPD is a third of it, the ceiling on this refactor is ~2,600 s of detector time, and 30-50% of *that* is a claim about the detector you haven't made yet.
